ZeroWiki 서비스 기획 인터뷰 전문
작성일: 2026-07-26
목적: ZeroWiki SaaS 서비스 기획 과정에서 진행한 질문과 사용자 답변 기록

======================================================================
인터뷰 배경
======================================================================

기존 NoteWiki는 다음 철학을 기반으로 운영되고 있었다.

- Raw Sources: 사용자가 보관하는 불변 원본
- Wiki: AI가 원본을 읽고 작성·갱신·연결하는 지식 계층
- Schema: AI가 따라야 할 구조와 운영 규칙
- Ingest: 새 원본을 기존 위키에 통합
- Query: 위키를 바탕으로 답하고 가치 있는 답을 다시 위키에 저장
- Lint: 모순, 낡은 주장, 고아 페이지, 누락 연결, 지식 공백 검사
- index.md: 지식 중심 색인
- log.md: 시간순 작업 기록

인터뷰 목적은 이 개인용 저장소 운영 방식을 소수 사용자가 실제로 사용할 수
있는 SaaS로 구체화하는 것이었다.


======================================================================
1차 인터뷰 — 제품의 존재 이유와 경계
======================================================================

[Q1]
이 서비스를 한 문장으로 설명한다면 무엇에 가장 가까운가?
자료를 넣으면 성장하는 개인 위키, 장기적으로 나를 기억하는 AI 파트너,
학습 도구, 실무 도구 중 무엇이 중심인가?

[A1]
사용자가 무엇을 원하는지에 따라 달라지는 것이 핵심이다.
하지만 큰 틀은 "나의 지식을 컨텍스트화한 도서관"과 같은 개념이다.
이를 학습 목적으로 쓸지, 실무 도구로 활용할지는 사용자가 원하는 바에
따라 다르게 구성된다.


[Q2]
NoteWiki가 반드시 해결해야 할 가장 큰 문제는 무엇인가?
"정리한 자료를 다시 찾는 비용이 새로 검색하는 비용보다 크다"가 여전히
가장 중요한 문제인가?

[A2]
맞다. RAG가 벡터 DB로 저장된 자료에서 원하는 내용을 찾는 것과 비슷하게,
내 지식을 정리해 둔 인덱스 기반의 거대한 도서관에서 LLM이 원하는 내용을
효과적으로 찾아주는 사서 역할을 맡는다.


[Q3]
사용자가 얻는 가장 핵심적인 결과는 무엇이어야 하는가?

[A3]
가장 핵심이 되어야 할 결과는 원하는 답을 빠르게 얻는 것,
그리고 자료들의 연결 관계를 발견하는 것이다.


[Q4]
"AI가 위키를 소유하고 사용자는 읽는다"는 현재 원칙을 서비스에서도
유지할 것인가? 사용자가 위키를 직접 편집할 수 있어야 하는가?

[A4]
기본적으로 위키 수정은 가능해야 한다.
하지만 직접 수정은 전혀 권장하지 않고, 오탈자나 어투 같은 자잘한 수정
외에는 전적으로 AI가 위키 작성을 맡기는 것이 좋다는 안내가 있어야 한다.
의미 있는 수정을 원한다면 현재 저장소에도 있는 Lint 기능을 이용하도록
권장한다.


[Q5]
AI가 객관적인 사실과 사용자의 기존 관점 사이에서 충돌을 발견하면
어떻게 수정해야 하는가?

[A5]
간단한 선택지 기반의 승인을 통해 수정한다.


[Q6]
AI가 기억해야 하는 사용자 정보의 범위는 어디까지인가?

[A6]
지극히 사적인 정보와 보안상 문제가 있는 정보를 제외한 대부분의 내용.


[Q7]
첫 번째 핵심 사용자는 누구인가?

[A7]
첫 번째 사용자는 한 분야를 깊게 학습하고자 하는 사람이다.
개발 학습은 하나의 예시다.

예:
- 해부학, 생리학 등의 자료를 학습하고 자신에게 적합한 식단과 운동 방법을
  추천받기를 원하는 사람
- 회사의 프로젝트 규칙이나 회의 자료를 정리해 두고 발표 자료나 보고서를
  작성할 때 레퍼런스를 찾고 싶은 사람


[Q8]
개인용 도구, 포트폴리오, 실제 SaaS, 장기 사업, 오픈소스 중 무엇을
우선 완성하려는가?

[A8]
소수 사용자를 받는 실제 SaaS.
성과에 따라 장기적인 사업화 가치도 충분하다고 본다.


[Q9]
서비스가 성공했다고 느낄 구체적인 순간은 무엇인가?

[A9]
지식 간 연결을 중요하게 본다.

- 문서 100개를 넣었는데 수동 분류 없이 연결된 위키가 생겼다.
- AI가 서로 다른 문서 사이의 모순을 먼저 발견했다.


[Q10]
사용자 간 연결 기능은 MVP에 어디까지 포함해야 하는가?

[A10]
다른 사용자의 페이지를 인용하거나 포크하는 정도까지는 MVP에 포함한다.
공동 편집은 제외하지만 편집 제안 기능은 있어도 좋다.
지식 그래프를 이용한 사용자 추천은 추후 확장으로 남긴다.


[Q11]
사용자가 자료를 넣는 방식의 우선순위는 무엇인가?

[A11]
자유로운 형식이 좋지만 기본적으로 Markdown 등의 문서가 우선이다.
Notion, Obsidian, Google Drive에서 대량 자료를 가져올 수 있으면
맥락 연결 측면에서 좋다.

우선순위:
1. Markdown 등의 문서와 Notion·Obsidian·Google Drive Import
2. AI 채팅 기록
3. 직접 작성한 메모 또는 회의록
4. 여러 웹사이트 자료, YouTube, GitHub 등


[Q12]
Ingest 때 자료마다 "왜 저장했는가, 현재 일과 어떻게 연결되는가,
무엇을 해보고 싶은가"를 인터뷰해야 하는가?

[A12]
사용자의 맥락과 연결되는 지점이 애매하다고 판단될 경우에만 질문한다.


[Q13]
자료를 넣은 직후 사용자에게 무엇을 가장 먼저 보여줘야 하는가?

[A13]
기존 지식과 연결된 부분을 먼저 보여준다.
그다음 후속 질문 사항을 추천한다.


[Q14]
AI 답변이나 새 종합을 위키에 환류할 때 어떤 정책을 사용할 것인가?

[A14]
저장 전 사용자 승인을 받는다.


[Q15]
화면은 Obsidian처럼 위키를 전면에 둘 것인가,
ChatGPT처럼 대화를 중심으로 둘 것인가?

[A15]
위키 탐색기와 AI 대화 정도만 전면에 내세운다.
문서 파일은 레퍼런스를 요구할 때만 드러나도록 한다.


[Q16]
제품을 사용할 때 어떤 감정을 느껴야 하는가?

[A16]
항상 강조하지만 내 지식을 담은 거대한 도서관이다.
제시된 비유 중에서는 "살아 움직이는 지식 지도"가 가장 가깝다.


[Q17]
그래프 뷰는 핵심 기능인가, 보조 시각화인가?

[A17]
보조 시각화가 주 기능이다.
추후 확장할 수 있지만 우선은 보조 기능으로 둔다.


[Q18]
Markdown 파일과 Git 저장소를 사용자가 언제든 가져갈 수 있는
진짜 원본으로 유지해야 하는가?

[A18]
사용자가 언제든 꺼내볼 수 있는 형태가 좋다.
GitHub와 비슷한 방식이 떠오른다.


[Q19]
로컬 우선과 클라우드 편의성 중 무엇이 중요한가?

[A19]
마음 같아서는 클라우드 동기화를 하고 싶다.
다만 서비스 복잡도와 기술적 난이도 측면의 추가 설명이 필요하다.


[Q20]
기술 스택, 월 운영비, 개발 인원, 출시 일정은 어떻게 생각하는가?

[A20]
기본은 Spring 중심이면 좋다.
서비스 구조에 더 적합한 스택이 있다면 적극적으로 추천받고 싶다.
월 운영비는 우선 10만 원 정도까지 가능하다.
서비스 운영 최소 기준도 함께 제시받고 싶다.
1인 개발이며 AI Agent를 이용해 개발할 예정이다.
첫 출시 일정은 기본 골조가 잡힌 다음 생각한다.

2차 인터뷰 — 지식 구조와 제품 정책
======================================================================

[Q21]
한 사용자가 여러 도서관을 만들 수 있어야 하는가?
도서관 사이의 지식을 서로 참조할 수 있어야 하는가?

[A21]
서로 참조 가능한 여러 개의 도서관을 생성할 수 있어야 한다.


[Q22]
도서관 생성 시 인터뷰를 통해 "도서관 운영 헌법"을 만드는 방식은
어떤가?

[A22]
괜찮다.
어느 정도 고정된 템플릿 질문으로 대략적인 가이드가 있으면 좋다.


[Q23]
학습·업무·건강 등 목적별 기본 템플릿을 제공할 것인가,
인터뷰만으로 완전히 동적으로 만들 것인가?

[A23]
"기본 템플릿 + 인터뷰를 통한 변형" 제안대로 한다.


[Q24]
하나의 원본 자료가 여러 도서관에 속할 수 있어야 하는가?

[A24]
공유되는 원본 자료 저장소를 공통으로 둔다.
여러 도서관에서 같은 파일을 참조하고 목적에 따라 다르게 해석할 수 있게 한다.


[Q25]
현재의 concept, flow, source 분류를 일반 분야에서도 유지할 것인가?
Source, Concept, Flow, Synthesis, Decision, Question 같은 범용 유형은
어떻게 생각하는가?

[A25]
도서관마다 필요한 분류를 AI가 적절히 판단해 두는 것이 좋다.


[Q26]
AI가 페이지를 어느 정도 단위로 나누어야 하는가?

[A26]
AI의 판단에 따른다.
현재 NoteWiki 저장소도 이를 따르고 있다.


[Q27]
사용자가 보는 위키 탐색기는 폴더형인가, 주제별 허브형인가?

[A27]
AI가 만든 주제별로 묶어서 보여준다.


[Q28]
AI가 모순을 발견했을 때 어떤 방식으로 해소할 것인가?

[A28]
사용자의 판단으로 채택할 수 있도록 한다.


[Q29]
출처 신뢰도를 AI가 평가해도 되는가?

[A29]
AI가 신뢰도를 판단하되 사용자가 수정할 수 있게 한다.


[Q30]
사실과 사용자의 개인적 판단을 명시적으로 분리해야 하는가?

[A30]
검증된 사실, 가설, 사용자의 개인적 판단을 각각 명시한다.


[Q31]
모든 AI 답변에 근거 페이지를 표시해야 하는가?

[A31]
사용자가 근거를 요구할 때만 표시한다.
단, 내부적으로는 근거와 출처를 계속 추적한다.


[Q32]
AI가 기존 지식을 수정하려 할 때 승인의 단위는 무엇인가?

[A32]
위험한 변경만 개별 승인하고 나머지는 전부 승인하는 형태로 한다.
전체 변경 세트를 먼저 보여주고, 모순·삭제·의미 변경 등의 위험 변경만
개별 선택하게 한다.


[Q33]
공개 단위는 도서관 전체인가, 개별 페이지인가?

[A33]
MVP에서는 개별 페이지만 공개한다.


[Q34]
포크한 페이지와 원본의 관계를 어떻게 유지해야 하는가?

[A34]
원본 업데이트 시 알림을 제공하고 버전을 비교할 수 있게 한다.
Lint 기능에 포크 원본 버전 변경으로 인한 내용 수정 필요 여부를 검사하는
기능도 추가한다.


[Q35]
포크한 페이지를 내 도서관 목적에 맞춰 AI가 다시 작성해도 되는가?

[A35]
가능하다. 내 도서관의 목적에 맞게 수정할 수 있다.


[Q36]
공개 전 민감정보, 기밀, 저작권 위험을 검사해야 하는가?

[A36]
공개 전 민감정보 등의 출처를 검사한다.


[Q37]
편집 제안은 누구나 보낼 수 있는가?

[A37]
도서관 소유자가 초대한 사용자만 보낼 수 있다.


[Q38]
MVP에 조직 공간을 포함할 것인가?

[A38]
MVP에서는 개인 계정의 비공개 도서관으로 좁힌다.
조직 공간은 추후 검토한다.


[Q39]
민감정보를 발견했을 때 어떻게 해야 하는가?

[A39]
개인정보나 기밀 자료에는 경고를 보낸다.
비밀번호나 API 키로 보이는 내용은 완전히 차단한다.


[Q40]
계정 삭제 시 데이터를 어떻게 처리할 것인가?

[A40]
계정 삭제 후 30일간 보관한다.
그 기간에는 복구할 수 있고, 30일 이후에는 완전히 삭제한다.


[Q41]
MVP에서 먼저 지원할 Import 경로 세 가지는 무엇인가?

[A41]
1. Obsidian 저장소 가져오기
2. 직접 파일 작성 및 업로드
3. Notion


[Q42]
외부 서비스 Import는 일회성인가, 지속 동기화인가?

[A42]
일회성 Import 방식으로 한다.


[Q43]
과금 방식은 무엇으로 할 것인가?

[A43]
월 구독 + 월 문서 처리량.


[Q44]
초기 사용자는 무료 테스터인가, 유료 사용자인가? 몇 명을 상정하는가?

[A44]
아직 상정하지 않았다.


[Q45]
첫 MVP가 증명해야 할 핵심 가설은 무엇인가?

[A45]
"사용자는 문서 100개를 넣은 뒤 AI가 만든 연결과 모순이 기존 검색·RAG보다
가치 있다고 느낀다"는 제안된 가설을 사용한다.

3차 인터뷰 — 실제 제품 동작과 MVP 경계
======================================================================

[Q46]
도서관 간 참조는 명시적으로 연결된 도서관에만 허용할 것인가?

[A46]
그렇다. 명시적으로 연결된 도서관만 참조할 수 있다.


[Q47]
도서관 간 참조에 방향성이 필요한가?

[A47]
단방향 참조로 한다.


[Q48]
질문할 때 연결된 도서관을 어떤 방식으로 검색할 것인가?

[A48]
현재 도서관을 우선 검색하고 근거가 부족할 때
"연결된 도서관도 찾아볼까요?"라고 확장 검색을 제안한다.


[Q49]
MVP 도서관 템플릿은 어떤 종류로 시작할 것인가?

[A49]
제안된 세 가지 중 다음 두 가지로 시작한다.

- 학습 및 연구
- 개인 의사결정

업무 레퍼런스 템플릿은 초기 MVP에서 제외한다.


[Q50]
온보딩 인터뷰는 어느 정도 길이가 적당한가?

[A50]
필수 질문 5개 정도로 시작한다.
자료를 넣으면서 도서관 설정과 운영 헌법을 점점 다진다.


[Q51]
AI가 만든 운영 헌법을 사용자가 직접 볼 수 있어야 하는가?

[A51]
그렇다.
자연어 요약을 보여주고 고급 설정에서 답변 깊이, 출처 우선순위,
분류 기준, 자동 연결 범위, 위험 변경 기준, 민감정보 정책 등을
수정할 수 있게 한다.


[Q52]
문서 100개를 가져오면 바로 모두 처리할 것인가,
먼저 전체 스캔과 처리 계획 승인을 거칠 것인가?

[A52]
먼저 전체를 빠르게 스캔한다.
중복, 중요 자료, 관련 자료 묶음, 민감정보, 처리 비용 등을 제시한 뒤
사용자가 처리 계획을 승인하면 본 처리를 시작한다.


[Q53]
Import 결과를 승인하기 전에 임시 위키를 탐색할 수 있어야 하는가?

[A53]
변경 내용을 승인 전에 미리 추적할 수 있다는 의미라면 좋다.
초안 상태에서 연결과 근거를 확인할 수 있게 한다.


[Q54]
안전한 변경과 위험한 변경의 기준을 어떻게 정할 것인가?

[A54]
다음 제안대로 한다.

자동 일괄 승인:
- 새 페이지
- 새 연결
- 요약 추가
- 오탈자와 문체 개선

개별 승인:
- 기존 사실 수정
- 내용 삭제
- 모순 판정
- 신뢰도 대폭 변경
- 페이지 병합·분할
- 포크 원본 변경 반영


[Q55]
AI가 맥락 질문을 해야 할 때 전체 처리를 멈출 것인가?

[A55]
해당 문서만 보류하고 나머지는 계속 처리한다.


[Q56]
Lint는 언제 실행할 것인가?

[A56]
- 대량 문서 Ingest 후 한 번
- 월간 정기 Lint


[Q57]
Lint가 지식 공백을 발견하면 웹 검색을 제안해야 하는가?

[A57]
그렇다.
위키 흐름상 중요한 곳이 공백이면 사용자 승인 후 웹에서 보완 자료를 찾는다.


[Q58]
지식 노후화 판단 기준을 도서관 템플릿별로 다르게 할 것인가?

[A58]
그렇다.
템플릿이 분야에 맞는 노후화 판단 기준까지 결정한다.


[Q59]
AI 사서가 별도 답변 모드를 제공해야 하는가?

[A59]
빠른 답변을 기본으로 한다.
사용자의 요청에 따라 학습, 비교, 의사결정, 보고서 등의 형식에 맞춘다.


[Q60]
AI가 위키에서 충분한 근거를 찾지 못하면 어떻게 해야 하는가?

[A60]
모른다고 답하고 필요한 자료를 제안한다.
웹 검색으로 가져올 수 있는 자료라면 웹 검색을 할지 사용자에게 묻는다.


[Q61]
새 종합을 위키에 저장하기 전에 무엇을 우선 보여줄 것인가?

[A61]
기존 페이지와의 연결, 근거와 출처를 최우선으로 보여준다.


[Q62]
전통 검색과 AI 대화를 분리할 것인가?

[A62]
둘 다 제공한다.
전통 검색은 페이지·주제·원본을 찾는 보조 검색이고,
AI 사서는 여러 페이지를 종합하는 중심 기능으로 둔다.


[Q63]
잘못된 의미 연결에 사용자가 피드백할 수 있어야 하는가?

[A63]
당연히 가능해야 한다.
사용자의 피드백으로 위키를 수정하고 이후 연결 및 검색 판단에도 반영한다.


[Q64]
어떤 이벤트에 알림이 필요한가?

[A64]
- 위험 변경
- 정기 Lint 결과
- 포크 원본 업데이트
- 편집 제안 도착
- 삭제 유예기간 만료 예정


[Q65]
알림 채널은 서비스 내부만으로 충분한가?

[A65]
초기에는 서비스 내부 알림만으로 충분하다.


[Q66]
초기 검증 그룹을 문서 50~200개를 가진 사용자 5~10명으로 정의해도 되는가?

[A66]
동의한다.
다만 AI가 직접 테스트한다는 의미인지, 그렇게 기획을 잡는다는 의미인지
설명이 필요하다.

[보충 설명]
이는 AI가 외부 참가자를 직접 모집한다는 뜻이 아니라,
제품 기획상 초기 검증 대상을 그렇게 정의한다는 뜻이다.
AI는 사용자 테스트 시나리오, 질문지, 성공 지표, 기록 양식, 결과 분석을
지원하고 실제 모집과 테스트 진행은 사용자가 담당한다.


[Q67]
무료 체험 제한을 어떻게 구성할 것인가?

[A67]
다음 제안대로 시작한다.

- 도서관 1개
- 원본 30개
- 제한된 AI 처리량
- 공개 페이지와 포크 사용 가능
- 유료 전환 후 여러 도서관과 대량 Import


[Q68]
사용자에게는 문서 수로 한도를 보여주되 내부적으로는 토큰 기준으로
처리량을 계산해도 되는가?

[A68]
그렇다. 내부적으로 토큰 기준으로 제한한다.


[Q69]
초기 서비스는 한국어 우선으로 만들 것인가?

[A69]
한국어 우선으로 한다.


[Q70]
MVP에서 제외할 기능을 확인한다.

후보:
- 실시간 공동 편집
- 조직 워크스페이스
- 로컬 폴더 양방향 동기화
- 자동 Notion 지속 동기화
- 고급 그래프 편집
- 사용자 관계 추천
- 모바일 네이티브 앱
- 자동 웹 크롤링
- 의료 진단 등 고위험 전문 판단

[A70]
웹 자료 추가를 위한 클리핑은 필요하다.
Obsidian Web Clipper처럼 간단한 웹 클리핑 기능을 추가하고,
자주 사용하는 사이트인 arXiv, YouTube 등에 대한 원본 추가 템플릿을
만들어 사용할 수 있게 한다.

나머지는 MVP 제외 사항이 맞다.

[보충 확정]
사용자가 URL 한 건을 지정하는 웹 클리핑은 MVP에 포함한다.
사이트 링크를 자율적으로 따라가는 광범위한 자동 크롤링은 제외한다.

[Q72]
"아카이브"는 arXiv를 의미하는가?

- YouTube
- arXiv 및 공개 논문 페이지
- GitHub 저장소·README
- 주요 블로그 플랫폼


[Q73]
로그인이 필요한 페이지와 유료 콘텐츠도 수집할 것인가?

[A73]
MVP에서는 공개 URL만 서버가 가져온다.
로그인·유료 콘텐츠는 사용자가 직접 파일이나 Markdown으로 제공한다.


[Q74]
웹페이지 이미지는 어떻게 처리할 것인가?

[Q75]
YouTube 자막이 없거나 가져올 수 없으면 어떻게 할 것인가?

처리 불가로 표시한다.


[Q76]
웹 원본 업데이트를 자동 감시할 것인가?

[A76]
자동 감시하지 않는다.
사용자가 다시 클리핑했을 때만 새 버전으로 반응한다.


[Q77]
로그인 후 첫 화면은 어떻게 구성할 것인가?

[A77]
다음 제안대로 한다.

- 중앙: AI 사서 입력창
- 왼쪽: 도서관과 주제 탐색기
- 상단: 전체 검색
- 보조 영역: 최근 Ingest와 Lint 등의 알림


[Q78]
도서관 첫 화면에서 무엇을 우선 보여줄 것인가?

[A78]
주요 주제와 AI가 발견한 연결을 우선 보여준다.


[Q79]
"살아 움직이는 지식 지도"를 어떻게 표현할 것인가?

[A79]
보조 그래프 뷰를 활용한다.
최근 Ingest 결과로 생긴 연결을 강조하고,
잔디 표시 등을 통해 사용자의 활동을 시각화한다.


[Q80]
페이지를 열었을 때 요약 카드를 먼저 보여줄 것인가,
문서 본문을 바로 보여줄 것인가?

[A80]
문서 본문을 바로 보여준다.


[Q81]
모바일 반응형 웹은 어디까지 지원할 것인가?

[A81]
자료 업로드와 승인까지 지원한다.
따라서 질문·답변, 페이지 읽기, 자료 업로드, 변경 승인이 모두 가능해야 한다.


[Q82]
위험 변경 승인 화면을 GitHub Pull Request와 유사하게 구성해도 되는가?

[A82]
그렇게 한다.

포함 정보:
- 변경 이유
- 영향을 받는 페이지
- 이전/이후 diff
- 근거 출처
- AI 신뢰도
- 승인·거절·수정 요청·판단 보류


[Q83]
사용자가 직접 본문을 크게 수정하려 할 때 어떻게 안내할 것인가?

[A83]
다음 제안대로 한다.

"이 페이지는 AI가 출처와 연결 관계를 함께 관리합니다. 직접 수정하면 일부
연결이나 근거가 불일치할 수 있습니다. 의미 변경이 필요하다면 AI 수정 또는
Lint를 권장합니다."

사용자가 계속하면 직접 편집을 허용하고 편집 후 자동 Lint 대상으로 등록한다.


[Q84]
잘못된 연결 피드백에서 이유도 함께 받을 것인가?

[A84]
이유를 받는다.
그 이유를 이후 운영 헌법에도 명시한다.

이유 예:
- 주제가 다름
- 인과관계가 아님
- 출처가 약함
- 도서관 목적과 무관함
- 중복 개념
- 기타


[Q85]
사용자의 연결 피드백을 현재 도서관에만 적용할 것인가,
모든 도서관에 적용할 것인가?

[A85]
기본은 현재 도서관에만 적용한다.
사용자가 원할 때 "내 모든 도서관에 적용"을 선택할 수 있게 한다.


[Q86]
Ingest 속도와 품질을 어떻게 조절할 것인가?

[A86]
2단계 처리 제안대로 한다.

1단계 저비용 모델:
- 분류
- 중복 후보
- 민감정보
- 구조 초안

2단계 고품질 모델:
- 핵심 종합
- 모순 판단
- 위험 변경


[Q87]
사용자가 실제 AI 모델을 직접 선택하게 할 것인가?

[A87]
모델명은 숨긴다.
빠른 처리, 표준 처리, 정밀 처리처럼 제품 모드만 제공한다.


[Q88]
AI 처리량이 부족할 때 어떻게 할 것인가?

[A88]
작업을 보류한다.
사용자가 추가 처리량을 구매하면 작업을 완료할 수 있게 한다.


[Q89]
초기 요금제를 무료, 개인 기본형, 개인 고급형,
추가 처리량 구매 형태로 구성해도 되는가?

[A89]
그렇다.

초기 가설:
- 무료: 도서관 1개, 원본 30개, 제한된 AI 처리량
- 개인 기본형: 여러 도서관, 월 처리량, 정기 Lint
- 개인 고급형: 더 많은 처리량, 정밀 Ingest, 대량 Import
- 추가 처리량 별도 구매


[Q90]
공개 페이지 발행 전 사용자가 검사 결과와 공개 정책을 최종 확인해야 하는가?

[A90]
그렇다.

확인 항목:
- 포함된 원본 출처
- 민감정보 검사 결과
- 공개하기 어려운 자료 경고
- AI 생성 내용 표시
- 포크 허용 여부
- 편집 제안 허용 대상


[Q91]
공개 페이지에 신고 기능이 필요한가?

[A91]
필요하다.


[Q92]
원본 문서 속 문장을 AI 시스템 명령으로 해석하지 않도록

[A92]
그렇다.


[Q93]
초기 사용자 5~10명의 분야를 어떻게 구성할 것인가?

[A93]
다음 제안대로 한다.

- 논문·전문 분야 학습 2명

[Q94]
사용자 테스트에서 참가자의 실제 자료 50~200개를 사용해야 하는가?

MVP 성공 기준을 다음과 같이 수치화해도 되는가?

WikiHub라는 웹사이트가 구상한 것과 비슷한 베타 서비스인 것 같다.
기획과 별도로 정보를 조사해 달라.

[조사 결론]
WikiHub는 Markdown 위키를 Git, API, MCP, 공개, 포크 기능으로 호스팅하는
"LLM 위키를 위한 GitHub"에 가깝다.

ZeroWiki는 자료를 목적별 지식 도서관으로 컴파일하고 사용자 인터뷰,
연결과 모순 탐지, 위험 변경 승인, 정기 Lint를 제공하는
"관리형 AI 사서"라는 점에서 중심 경험이 다르다.


======================================================================
인터뷰를 통해 확정된 서비스 요약
======================================================================

제품:
사용자의 자료를 목적별로 연결하고 모순을 관리하는 개인 지식 도서관.

핵심 경험:
- 원하는 답을 빠르게 얻음
- 자료 사이의 연결 발견
- 서로 다른 출처의 모순 선제 발견

도서관:
- 여러 개 생성 가능
- 명시적인 단방향 참조
- 공통 원본 보관소 공유
- 학습·연구 / 개인 의사결정 템플릿
- 5문항 온보딩 후 점진적으로 운영 헌법 강화

입력:
- Obsidian
- 직접 작성 및 파일 업로드
- Notion 일회성 Import
- URL 웹 클리핑

AI 운영:
- 저비용 스캔 + 고품질 종합의 2단계 처리
- 맥락이 불분명한 문서만 보류
- 안전한 변경 일괄 승인
- 위험 변경 Pull Request형 승인
- 대량 Ingest 후 Lint와 월간 정기 Lint

신뢰:
- 사실, 출처 주장, AI 종합, 사용자 판단, 가설 구분
- AI가 출처 신뢰도를 제안하고 사용자가 수정
- 근거는 내부적으로 항상 추적하고 요청 시 표시

공개:
- 개별 페이지만 공개
- 포크, 업데이트 알림, 버전 비교
- 초대 사용자만 편집 제안
- 공개 전 민감정보·기밀·저작권 위험 검사
- 신고 기능

소유권:
- Markdown 전체 내보내기
- 버전과 diff
- 장기적으로 GitHub 미러링 고려

과금:
- 월 구독 + 월 처리량
- 사용자에게는 문서 기준으로 안내
- 내부적으로는 토큰 기준으로 계산
- 처리량 부족 시 작업 보류 및 추가 구매

MVP 제외:
- 실시간 공동 편집
- 조직 워크스페이스
- 로컬 폴더 양방향 동기화
- Notion 지속 동기화
- 사이트 전체 자동 크롤링
- 웹 원본 자동 변경 감시
- 고급 그래프 편집
- 사용자 관계 추천
- 모바일 네이티브 앱
- 의료 진단 등 고위험 전문 판단

핵심 검증 가설:
"사용자는 문서 100개를 넣은 뒤 AI가 만든 연결과 모순이 기존 검색 또는
RAG보다 가치 있다고 느낀다."
